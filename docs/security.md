# Security & Privacy Notes

## What TransferCLI logs

By design, **TransferCLI does not log uploader IP addresses or any per-request metadata of its own**:

- `nginx access_log off` (in the bundled vhost)
- transfer.sh and the admin panel listen on `127.0.0.1` and only ever see the local proxy's address
- transfer.sh stores no uploader info in file metadata; the admin panel has no uploader-tracking column
- No analytics, no cookies, no telemetry

transfer.sh does write upload file names to the systemd journal (`journalctl -u transfercli`). Failed admin
logins are logged with the client address the proxy passes in `X-Real-IP`.

## What TransferCLI persists

| Path | Contents | Mode |
|---|---|---|
| `/var/lib/transfercli/uploads/` | uploaded files + JSON metadata (size, type, downloads, expiry) | `transfercli`, 0750 |
| `/etc/transfercli/.htpasswd` | admin credentials (bcrypt) | `root:transfercli` 0640 |
| `/etc/transfercli/upload.htpasswd` | upload credentials (bcrypt) | `root:transfercli` 0640 |
| `/etc/transfercli/transfersh.env` | auth/limit settings for transfer.sh | `root:transfercli` 0640 |
| `/etc/transfercli.env` | purge settings, written by the admin panel | `root:transfercli` 0660 |
| `/root/transfercli-credentials.txt` | passwords generated by the installer | `root` 0600 |

## Hardening in 2.0

### Supply chain
- transfer.sh is **compiled from source** (`backend/`), pinned to a reviewed upstream commit through
  `backend/go.mod` + `go.sum`, with a current Go toolchain. The upstream v1.6.1 release binary (Go 1.21.4,
  December 2023) is affected by 110 known vulnerabilities in the Go standard library and dependencies;
  TransferCLI no longer downloads it.
- CI runs `govulncheck` on both modules; a release is not published when it reports a reachable vulnerability.
- The installer installs a **pinned release tag** and verifies every binary against the release's
  `SHA256SUMS`. It refuses to install on a mismatch. Install from a tag URL and read the script first.

### Upload endpoint
- Uploads (`PUT`/`POST`) require HTTP Basic credentials from `/etc/transfercli/upload.htpasswd` by default.
  Downloads stay public (anyone with the link). `TC_PUBLIC_UPLOADS=1` turns the password off — only do
  that on a private network: an open upload endpoint on the internet is quickly used for malware and
  phishing hosting.
- Optional limits: `TC_MAX_UPLOAD_MB` (per upload) and `TC_RATE_LIMIT` (requests per minute per client).
  The bundled nginx overwrites `X-Forwarded-For`/`X-Real-IP` so clients cannot spoof the address transfer.sh
  rate-limits on. If you use your own proxy, do the same (see [nginx.md](nginx.md)).
- transfer.sh sanitises HTML/SVG/XML when a file is shown inline and serves other downloads as attachments.

### Admin panel
- Authenticates every request itself against a bcrypt htpasswd file (`TC_ADMIN_HTPASSWD`); MD5/SHA/plain
  hashes are refused. Failed logins are throttled (20 per minute, then HTTP 429 until the minute ends).
- **CSRF protection**: delete, bulk delete, expiry and settings requests must come from the panel's own
  origin (`Origin`/`Referer`, `Sec-Fetch-Site`). Browsers resend Basic credentials to cross-site requests,
  so without this any web page could make an admin's browser delete files.
- File names and content types are chosen by uploaders. The panel never inserts them as HTML (no
  `innerHTML`), percent-encodes file links, and sends a strict Content-Security-Policy,
  `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`.
- Listens on `127.0.0.1` only. Serving the panel on its own host name (separate origin from the uploaded
  files) adds one more layer: set `TC_BASE_URL` to the file host and route `/admin/` only on the admin host.

### Services
- Both services run as the unprivileged `transfercli` user with `NoNewPrivileges`, `ProtectSystem=strict`,
  an empty capability bounding set, a syscall filter and private `/tmp`; only `/var/lib/transfercli` (and,
  for the admin panel, `/etc/transfercli.env`) is writable. `systemd-analyze security` rates both 1.5 (OK).
- Saving settings no longer uses `sudo`: `transfercli-config.path` notices the changed file and restarts
  transfer.sh.

## Threat model & recommendations

### Disk exhaustion
An upload user can fill the disk. Mitigations: `PURGE_DAYS`, `TC_MAX_UPLOAD_MB`, a dedicated filesystem or
volume for `/var/lib/transfercli`, and monitoring (the admin panel shows a disk usage bar).

### Abuse
Keep uploads password-protected, rotate the upload password when it leaks (re-run the installer with
`TC_UPLOAD_PASSWORD=…`), and use `TC_RATE_LIMIT` or proxy rate limits.

### Upgrading
Re-run the installer of the new release; it replaces the binaries and units and keeps data and credentials.
Watch the repository's releases — security fixes are listed in [CHANGELOG.md](../CHANGELOG.md).

### Data at rest
File contents and metadata are stored unencrypted. If you need encrypted storage use LUKS for the
underlying block device or `gocryptfs` for `/var/lib/transfercli`.
